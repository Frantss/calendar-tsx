## Events

An event is either timed or all-day. Both carry a unique `id` and a `data` payload of your type `TData`.

```ts
import type { Calendar_EventInput } from '@calendar-tsx/core';

type Booking = { title: string };

const events: Calendar_EventInput<Booking>[] = [
  {
    id: 'standup',
    start: Temporal.ZonedDateTime.from('2026-03-11T09:00[America/New_York]'),
    end: Temporal.ZonedDateTime.from('2026-03-11T09:15[America/New_York]'),
    data: { title: 'Standup' },
  },
  {
    id: 'offsite',
    allDay: true,
    start: Temporal.PlainDate.from('2026-03-12'),
    end: Temporal.PlainDate.from('2026-03-13'),
    data: { title: 'Offsite' },
  },
];
```

| Field         | Timed                    | All-day                                              |
| ------------- | ------------------------ | ---------------------------------------------------- |
| `id`          | `string`, unique         | `string`, unique                                     |
| `allDay`      | —                        | `true`                                               |
| `start`       | `Temporal.ZonedDateTime` | `Temporal.PlainDate`                                 |
| `end`         | `Temporal.ZonedDateTime` | `Temporal.PlainDate`, inclusive; defaults to `start` |
| `resourceIds` | `string[]`, optional     | `string[]`, optional                                 |
| `data`        | `TData`                  | `TData`                                              |

- **Time zones.** Timed events may be in any zone; they are converted to the calendar's `timeZone` before layout.
  Events in the layout are these converted copies.
- **Midnight ends.** A timed event ending exactly at midnight ends on the previous day, so a 22:00–00:00 event stays on
  one day.
- **Unique ids.** In development, duplicate ids log an error. Ids also key the layout's segments.
- **Hiding.** There is no hidden flag: filter the array you pass in.

## Order

Events in the visible range are sorted before layout, which decides bar rows and lane order. The default order is:

1. Earlier start date first.
2. Longer date spans first.
3. All-day before timed.
4. Earlier start time first.

Pass `eventOrder(a, b, context)` to replace it. `context` carries the view key and kind, so the order can differ per view.

## Resources

Resources become columns in a time-grid view with `groupBy: 'resource'`, in the order you pass them.

```ts
import type { Calendar_Resource } from '@calendar-tsx/core';

const resources: Calendar_Resource<{ color: string }>[] = [
  {
    id: 'room-a',
    title: 'Room A',
    availability: [
      {
        start: Temporal.ZonedDateTime.from('2026-03-11T09:00[America/New_York]'),
        end: Temporal.ZonedDateTime.from('2026-03-11T17:00[America/New_York]'),
      },
    ],
    data: { color: 'teal' },
  },
];
```

- An event appears in every column whose resource id is in its `resourceIds`. Events without `resourceIds` appear in
  no resource column.
- `availability` is a list of absolute intervals. The gaps between them become `unavailable` segments in each column.
- A resource with no availability on a day is marked `isUnavailable` for that day and shaded across it.

## Managed event store

If you have no cache of your own, `createEventStore` keeps an event list in a TanStack Store. Pass its
`events` to the calendar like any other input.

```ts
import { createEventStore } from '@calendar-tsx/core';

const eventStore = createEventStore<Booking>(events);

eventStore.add([newEvent]); // upserts by id
eventStore.update('standup', event => ({ ...event, data: { title: 'Daily standup' } }));
eventStore.remove('offsite');
eventStore.reset([]);

eventStore.store.state.events; // pass as the calendar's `events`
```

Every change produces a new array, so the calendar re-derives when you pass it in. Don't use it to mirror another
store; pass that store's data directly.
