## `useCalendar`

```ts
const calendar = useCalendar(() => options);
```

Takes an accessor returning the same [options](/docs/core/options) as `createCalendar`, and returns the
[instance](/docs/core#the-instance).

- The instance is created once, from the options read untracked.
- It mounts with the owner, which starts the clock, and unmounts on cleanup.
- A render effect passes `options()` through `~update`, and reruns whenever a signal read inside the accessor changes.
  The state re-derives only when a [tracked option](/docs/core/options) changed, so keep `views`, `features`, `events`
  and `resources` referentially stable.

Read signals inside the accessor (`view: view()`), not outside it, or changes won't reach the calendar.

<Callout type='warn' title='Let the types infer'>
  Don't pass type arguments such as `useCalendar<Booking>(…)`: TypeScript then stops inferring the rest, and `view` and
  `onNavigate` widen to `string`. Type `events` instead, for example as `Calendar_EventInput<Booking>[]`.
</Callout>

## `CalendarProvider`

```tsx
<CalendarProvider value={calendar} locale='en-GB'>
  {children}
</CalendarProvider>
```

Puts an instance in context for the parts and `useCalendarSelector`. Every part must render inside a
`CalendarProvider` or `Calendar`, or it throws.

| Prop     | Type                  | Default   | Description                                      |
| -------- | --------------------- | --------- | ------------------------------------------------ |
| `value`  | The calendar instance | —         | Usually from `useCalendar`.                      |
| `locale` | `string`              | `'en-US'` | Locale for the parts' default accessible labels. |

## `Calendar`

```tsx
<Calendar timeZone='UTC' views={views.views} features={{ ...views.features }} view={view()} date={date()} {...rest}>
  {children}
</Calendar>
```

`useCalendar` and `CalendarProvider` in one component. It takes the calendar options as props, including `locale`, and
re-syncs when they change. Use it when nothing outside the tree needs the instance.

## `useCalendarSelector`

```ts
const layout = useCalendarSelector((state: State) => state.layout);

layout(); // the current layout
```

Selects from the calendar's [state](/docs/core/layouts) in context and returns an accessor that updates when the
selected value changes.

The context cannot carry the instance's types, so the state defaults to the widest type. Annotate the selector's
parameter with `Calendar_StateOf<typeof calendar>`, or build the type from your views:
`Calendar_State<TData, TResourceData, typeof views.views>`.

To narrow to one layout kind, derive it, then use `<Show>`:

```tsx
const grid = () => {
  const current = layout();

  return current.kind === 'timeGrid' ? current : undefined;
};

<Show when={grid()}>{grid => <TimeGridView model={grid()}>{/* … */}</TimeGridView>}</Show>;
```

## `useCalendarContext`

Returns `{ instance, locale }` from the nearest provider, with the instance's types erased. Parts use it; you rarely
need it.

## `useCalendarEventStore`

```ts
const eventStore = useCalendarEventStore<Booking>(initialEvents);

const calendar = useCalendar(() => ({ ...options, events: eventStore.events() }));

eventStore.add([booking]);
```

The [managed event store](/docs/core/events-and-resources#managed-event-store). It returns the store's `add`, `update`,
`remove` and `reset`, plus `events`, an accessor for the current list.
