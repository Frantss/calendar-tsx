<section id='input'>

An event is timed or all-day, as its `kind` says. Both carry a unique `id` and a `data` payload of your own type.

<include lang='ts'>../../../examples/core/setup.ts#events</include>

| Field         | Timed                              | All-day                                              |
| ------------- | ---------------------------------- | ---------------------------------------------------- |
| `id`          | `string`, unique                   | `string`, unique                                     |
| `kind`        | `'timed'`                          | `'allDay'`                                           |
| `start`       | `Temporal.ZonedDateTime`           | `Temporal.PlainDate`                                 |
| `end`         | `Temporal.ZonedDateTime`           | `Temporal.PlainDate`, inclusive; defaults to `start` |
| `resourceIds` | `string[]`, optional               | `string[]`, optional                                 |
| `display`     | `'auto' \| 'background'`, optional | `'auto' \| 'background'`, optional                   |
| `data`        | `TData`                            | `TData`                                              |

- Timed events may be in any zone. The calendar converts them to its `timeZone`, and the model holds the converted
  copies.
- A timed event ending exactly at midnight ends on the previous day, so 22:00 to 00:00 stays on one day.
- Duplicate ids log an error in development. Ids also key the model's segments.
- Pass a new array to change events; the calendar compares the array by reference.
- `display: 'background'` shades the event's time instead of laying it out. See
  [background events](background-events).

`createEvent` returns its argument. Use it to type an event where you write it, with `kind` kept as a literal and the
payload type inferred from `data`:

For repeating events, add the optional [recurrence feature](recurrence). One-off and recurring definitions share
the same `events` array and event store.

## Hiding events

There is no hidden flag: filter the array. Memoize the result, so the calendar only re-derives when it changes.

<section id='order'>

## Order

The calendar sorts the events in the visible range before layout, and the order sets bar rows and lanes. The default order is:

1. Earlier start date first.
2. Longer date spans first.
3. All-day before timed.
4. Earlier start time first.

Pass `eventOrder(a, b, context)` to replace it. `context` carries the view key and `kind`, so the order can differ per
view. It is read when the layout derives: changing it alone does not re-order until a tracked option changes.

</section>

<section id='store'>

## Event store

If you have no data cache of your own, the event store keeps the list for you. `add(events)` upserts by id, `update(id, event => next)` replaces one event, `remove(id)` deletes one and
`reset(events)` replaces the list. Every change produces a new array. Don't use it to mirror another store; pass that
store's data directly.

</section>
