An agenda: the days that have events, each with its events in order.

<CalendarPreview view='agenda' />

```ts
import { listView } from '@calendar-tsx/core';

listView({ days: 7 });
listView({ period: 'month' });
listView({ period: 'quarter' });
listView({ months: 3 });
listView({ weeks: 1, hiddenDays: [6, 7] });
```

Choose exactly one of `days`, `weeks`, `months`, or `period`. Counts must be positive integers.

| Duration    | Meaning                                                                |
| ----------- | ---------------------------------------------------------------------- |
| `days: N`   | N dates from `date`; `7` keeps its existing week alignment.            |
| `weeks: N`  | N whole weeks from `firstDayOfWeek`.                                   |
| `months: N` | N calendar months from the first day of the anchor month.              |
| `period`    | `'month'`, `'quarter'`, or `'year'`, aligned to its calendar boundary. |

`next()` and `prev()` advance the configured duration. Month-based steps land on the first day. `hiddenDays` omits ISO weekdays (`1` Monday to `7` Sunday) without changing the nominal period or its inclusive fetch range; at least one weekday must remain visible.

Only days with at least one event are listed, so a quiet range has no days; render an empty state for it.

`hiddenDays: [6, 7]` hides Saturday and Sunday using ISO weekdays (Monday `1`, Sunday `7`).

Hiding all seven weekdays is invalid. A controlled date with no visible weekdays produces an empty layout.
## Resource grouping

Reuse the same factory for an agenda grouped by resource:

```ts
listView({ weeks: 1, groupBy: 'resource' });
listView({ weeks: 1, groupBy: ['resource', 'date'] });
listView({ weeks: 1, groupBy: ['date', 'resource'] });
```

`'resource'` and `['resource']` put resources first, followed by their dates. The ordered pairs choose whether the outer sections are resources or dates. Omitting `groupBy`, `'date'`, and `['date']` produce the ordinary agenda. Keys cannot repeat, and month grouping is specific to day grids.

Resources follow their input order, and dates are chronological. Events assigned to several known resources appear in each matching group. Unassigned events and unknown-resource assignments are excluded from resource agendas, as in resource grids and timelines. Ordinary agendas include them. Empty dates and resources are omitted, so an agenda with no matching events has one list-wide empty state.

### Resources before dates

With `groupBy: 'resource'` or `['resource', 'date']`, each section names a resource and lists its dates.

### Dates before resources

With `groupBy: ['date', 'resource']`, each section shows a date and lists the resources with events on that date.

Render `layout.sections` with `ListViewSection` and `ListViewSectionHeader` to show the grouping headings. The day headings show dates in resource-first lists and resource names in date-first lists. Both orders work with all list durations and `hiddenDays`.

## Date headings

The supplied themes place the date beside its event rows. Give `ListViewDayHeader` a `<time dateTime={day.date.toString()}>` containing a `<strong>` day number and a `<span>` with the weekday and month/year. The React and Solid examples show this composition. The full date remains the heading's accessible name, and date formatting belongs to your application.

The date column narrows with the list, and its labels wrap when space is limited. Override `--calendar-list-date-width` (default `10rem`) to cap its width. `ListViewDay` emits `--cal-events` so the heading spans that day's event rows; render the header and events as direct children of the day.

## Model

`layout` is `{ kind: 'list', coordinates, sections, days }`.

- Each section is `{ key, resource?, date?, days }`. `resource` identifies a resource-first section; `date` identifies a date-first section. Ordinary lists have one section with neither field.
- Each day is `{ key, date, resource?, events }`. Grouped day keys identify both the date and resource.
- `layout.days` is a flat index of the same day objects in section order. Existing consumers can keep using it; section headings require iterating `sections`.

`Calendar_ListLayout`, `Calendar_ListSection`, and `Calendar_ListDay` take event data, resource data, and features as their generic parameters. If a feature decorates days, update the sections and rebuild the flat index from those days.
