<section id='intro'>

Features add behavior beyond navigation, the event pipeline and the clock. Call a feature factory with its default
configuration, then collect the definitions with `calendarFeatures`. `calendarViews` binds the registry to your
named view definitions. View factories supply layouts automatically.

See [selection and event editing](../features/interactions) for built-in operations and browser bindings.

</section>

<section id='registering'>

Every view inherits the registered features. A view's `features` object contains configuration overrides keyed by
registry alias. Adding an override to one view does not change another view's participation.

Unknown override keys and invalid configuration types are errors. Pass the same registry to `calendarViews` and
the calendar. Feature definitions and factory defaults are fixed at calendar creation; keep them at module scope
or memoize them. To update an override, supply a new view definition and a new `views` map.

</section>

<section id='rest'>

## Settings

Each factory defines its configuration input shape. For example, `backgroundFeature(layers)` takes an array, and
`recurrenceFeature()` takes no configuration. An override uses that same shape. Hooks read the resolved value
through `context.config`.

An omitted override inherits the factory defaults. Object overrides shallow-merge with defaults. Arrays replace
them; use an explicit spread to extend an array. An empty background array clears the view's layers while keeping
the feature registered. Nested objects are replaced rather than recursively merged.

The runtime caches resolved configuration per view definition and includes its identity in stage dependencies.
There is no generic switch to remove a registered feature from a view. Interaction operations and input drivers
support `enabled: false` in their own configuration. Duplicate registrations of one feature identity are rejected.

## State

A feature declares state slices with `getInitialState`. They appear on `calendar.store.state`, and each slice lives in
one of three places:

| Ownership    | How                                            | Writes through `setState`                     |
| ------------ | ---------------------------------------------- | --------------------------------------------- |
| Uncontrolled | Default; the calendar keeps it.                | Update the slice.                             |
| Controlled   | Pass the value in `state: { slice }`.          | Ignored; the slice changes only with `state`. |
| External     | Pass a store in `atoms: { slice }`, read once. | Update the store.                             |

An atom is any `{ state, setState(updater) }`, so a TanStack Store fits. A controlled slice reports nothing by itself:
a feature that supports control calls its own configured `on…Change` callback. State and actions belong to the
calendar instance and are shared across its views. Factories and view assembly do not initialize state.

## Writing a feature

<include lang='ts'>../../../examples/features/highlight-feature.ts#feature</include>

Return a `Calendar_ConfiguredFeature<'yourFeatureIdentity', YourConfig>` from the factory. `~id` is the stable
identity used by declaration maps and event sources; `~config` contains resolved factory defaults. A definition
whose `~config` is `undefined` takes no configuration overrides. The optional `~validateConfig` function can check
configuration values at runtime, including merged view overrides.

Features can supply these optional members:

| Member            | Description                                                                              |
| ----------------- | ---------------------------------------------------------------------------------------- |
| `getInitialState` | Returns the initial value of each state slice the feature owns.                          |
| `constructApi`    | Returns actions, merged onto `calendar.api`.                                             |
| `requires`        | Canonical feature identities required before APIs can install.                           |
| `interaction`     | Optional operation descriptor, settings key, validators and dependencies.                |
| `resolveEvents`   | Resolves definitions carrying the feature's stable source identity before normalization. |
| `events`          | A stage over events after the core sort, before layout.                                  |
| `decorate`        | A stage over the built layout; adds the feature's model fields.                          |

A stage is `{ deps?, run }`. It reruns when its input, resolved configuration or one of its `deps` changes. List
other values read by `run` in `deps`. Configured stages run in registry order. Source resolution remains
calendar-wide and uses the registered implementation rather than creating a resolver for each view.

The stage and action hooks receive a context:

| Member                      | Description                                                         |
| --------------------------- | ------------------------------------------------------------------- |
| `config`                    | Resolved factory defaults and active-view overrides.                |
| `options`                   | The calendar's current core options.                                |
| `view`                      | The active view, with its settings.                                 |
| `api`                       | The calendar's API.                                                 |
| `features`                  | Resolved definitions keyed by canonical feature identity.           |
| `state`                     | Current calendar state when a command runs.                         |
| `layout`                    | Active layout model, input, settings and capabilities.              |
| `onOptionsChange(callback)` | Runs after each options sync.                                       |
| `onMount(callback)`         | Acquires resources and returns cleanup for the mounted lifetime.    |
| `settings(key, defaults)`   | Reads interaction defaults, live options and active-view overrides. |
| `getState(key)`             | A state slice, from wherever it lives.                              |
| `setState(key, updater)`    | Writes a state slice; see [state](#state).                          |

## Typing a feature

Contributions use declaration merging into feature maps keyed by the definition's stable `~id`. Consumer aliases
can differ: registering `highlight: highlightFeature()` still selects the `highlightFeature` map entries.
Configuration types travel on the factory result. Interaction features additionally use `Calendar_Options_FeatureMap<TData, TResourceData>` for live callbacks and ownership inputs; API maps receive the same payload types.

| Map                                   | Adds                                                |
| ------------------------------------- | --------------------------------------------------- |
| `Calendar_EventInput_FeatureMap`      | Event definitions resolved by the feature.          |
| `Calendar_State_FeatureMap`           | State slices, also accepted by `state` and `atoms`. |
| `Calendar_Api_FeatureMap`             | Actions on `api`.                                   |
| `Calendar_DayGridDay_FeatureMap`      | Fields on day-grid days.                            |
| `Calendar_BarSegment_FeatureMap`      | Fields on bar segments.                             |
| `Calendar_TimeGridColumn_FeatureMap`  | Fields on time-grid columns.                        |
| `Calendar_TimeGridSegment_FeatureMap` | Fields on time-grid segments.                       |
| `Calendar_ListDay_FeatureMap`         | Fields on list days.                                |
| `Calendar_TimelineRow_FeatureMap`     | Fields on timeline rows.                            |
| `Calendar_TimelineSegment_FeatureMap` | Fields on timeline segments.                        |

Every registered feature contributes to every supported view model. Layout feature maps receive canonical
feature keys, so aliases do not affect model composition. Use `Calendar_StateOf<typeof calendar>` for typed
selectors. Providers accept calendars independently of which feature-state maps are imported.

## Operation lifecycle

`interactionFeature()` constructs one transient runtime from the resolved descriptors. Register operation features
independently with `dateSelectionFeature()`, `eventMoveFeature()` and `eventResizeFeature()`. Their programmatic APIs install
through `constructApi` on both core and adapter instances. Mount `useCalendarInteractions` or the core DOM host to attach pointer listeners.

Third-party features declare their intent, target and result in `Calendar_OperationMap<TData>`, provide a descriptor
with `createInteractionOperation`, and add `interaction: { operation, validate?, deps? }`. A `settings` key on this
contribution exposes resolved factory configuration on the corresponding operation input field. They also extend the usual
API/options maps and declare `requires: ['interactionFeature'] as const`. Targets can be non-date values; callbacks
and results retain consumer data. Dependency values compare by reference; use primitive setting fields or stable
input references. Shared controls expose no unrestricted begin/evaluate route.

Drafts live in a readonly TanStack store at `api.interactions.store`; draft changes do not rebuild the base layout.
Selection writes its accepted range through D29 state. Event changes remain callback proposals for the consumer.
Option-update and mount hooks refresh current inputs and cancel sessions at final unmount. Constructed APIs and
subscriptions survive remount. Core callers use `~mount`/cleanup and `~update`; adapter hooks drive them automatically.

## Layout features

A layout feature supplies a view kind:

| Member    | Description                                                       |
| --------- | ----------------------------------------------------------------- |
| `kind`    | The layout's `kind`.                                              |
| `period`  | `(date, settings, { firstDayOfWeek })` → the nominal period.      |
| `range`   | `(period, settings, { firstDayOfWeek })` → the visible days.      |
| `step`    | `(date, settings, direction)` → the date one period away.         |
| `build`   | `(input, settings)` → the layout model.                           |
| `locate`  | Optional conversion from a surface position to a semantic target. |
| `project` | Optional conversion from a proposal to preview geometry.          |

`build` receives `range`, `period`, `inputRange`, foreground and background events, resources, `timeZone` and `now`;
`settings` is the view definition. A new kind also needs an entry in `Calendar_Layout_FeatureMap`, keyed by the
layout feature's name. Its view supplies the layout implementation; it is not a configured registry entry.

Day-grid, time-grid and timeline implement `locate/project`. Register `interactionFeature` to call them through
`api.interactions` and observe derived `store.state.preview`. Missing capabilities return `unavailable`; semantic
operations still work. Draft previews use separate overlays and do not rebuild the base model.

Third-party layouts extend `Calendar_LayoutInteractionMap`, keyed by layout kind, with `point`, `target` and
`geometry` types. Annotate their descriptor with `Calendar_LayoutFeature<'myKind', MySettings, MyModel>`.
Both capabilities receive the decorated model, the actual layout input and the active view settings. The runtime
dispatches to that descriptor without a builtin-kind switch. Controlled/external draft ownership stores semantic
snapshots only; preview geometry derives locally from the draft and base model.
